# Bug 排查方法论

## 核心原则

**不凭空猜测，用数据说话。但数据不是终点 —— 先复现，再定位，再理解根因。**

最常见的失败：把"能复现"当成"已定位"。定位到出错的**位置** ≠ 找到**根因**。
改症状不改根因，换一批数据就复发。

## 第 -1 步：列假设（不能跳过）

**触发**：用户报了症状（"打不开""报错了""不对"），但没给一手错误信息。

**这一步在"复现"之前**，因为拿不到报错时，"先复现"会逼你造假。

### 自造证据 —— 最毒的一类错误

**真实案例**：只有一个假设时，它要么被证实要么思路断掉 —— 于是自己造一个输入去测：

```
编了个接口名 app.init → curl 测出 404 → "我测出来的，是事实"
→ 推出"nginx 没配 PATH_INFO"
→ 用户纠正后，重跑同一实验、得到同一 404 → 坚信自己没错
```

**为什么最毒**：下游全程都是真的（404 真、命令真跑过）。唯一假的那环在**最上游**，
且已消失在过程里 → 所以"再验证一次"救不了，重跑同假输入得同真输出。

### 所以

1. **开局列 ≥2 个假设**（代码 / 配置 / 构建产物 / 缓存 / 第三方）。
   只列一个 = 逼自己去证实它 = 造证据的动力。
2. **每个假设配反证条件**：什么现象出现就认它错。
   反证条件里要写明**能从代码里读到的真实名字**，编造的自动不能用。
3. **卡住两轮就换假设**，不是在同一假设上加细节。
4. **领域外的先声明无取证能力**（构建产物在不在 / 缓存 / 第三方后台行为），
   要用户提供事实，**不要脑补**。

**结论所依据的每个具体名字（接口/字段/报错文本/路径）必须指得出处（文件:行）。**
指不出的只能标"推测"，**不得当证据用**。

> **为什么多假设能防造假**：单假设必须被证实，否则思路断 → 有动机造。
> 多假设下，"支持了 A" ≠ "就是 A"（B/C/D 还没排除）→ 假证据推不出结论，造它就没意义。

## 第 0 步：复现

没有稳定复现，后面全是猜。

- 复现的必要条件是什么？哪个输入/操作/环境触发？
- 100% 复现还是偶发？偶发先找触发模式（特定数据/时机/顺序）。
- 有现成错误栈吗？**错误信息 + 行号是最便宜的定位入口。**

**给 Bug 起个名字**（一句话描述 + 触发条件）。卡住时回来核对是否还在同一个 Bug 上。

## 第一步：定位范围 —— 改动了什么

Bug 不会凭空出现。先查最近的改动：

```bash
git diff HEAD~3 --stat           # 改了哪些文件
git log -p -S '可疑字段/函数名'   # 谁改过这段
git blame <file> -L <行号,行号>   # 定位到具体某行
```

问自己：这次新增/修改了什么？涉及哪些文件？哪个最可能影响出问题的地方？

**别排查无关代码。**

## 第二步：让数据说话

不猜，打印出来看。

- **打印关键数据，不要只打印"到了这里"** —— 要打印实际的变量值、类型、入参出参。
- **二分法**：在可疑链路上隔几层插日志，先跑一遍看哪段有数据、哪段没有，
  范围砍半再往里加。比一次打满所有层更快收敛。
- **带唯一前缀**（如 `[BUG-01]`）：日志里 grep 一次看到全链路顺序。
- 怀疑并发/时序时，打时间戳与调用来源。

## 第三步：顺藤摸瓜

从用户操作出发，沿调用链一层层往下：入口 → 路由 → 中间件 → 业务层 → 数据层 → 存储。

**每一层打印关键数据，找到数据从正确变为错误的那一层 —— bug 就在那一层。**

## 第四步：找根因，不只修症状

修复前回答：

- 为什么数据在这一层变错了？**逻辑错误**（判断写反/取错字段）、
  **类型错误**（null/数组/对象混用）、还是**数据本身脏**（上游写入时就错）？
- 根因若在上游，这里 patch 只是挡一下 —— 应该去修上游，或在入口统一兜底。

**修一层，不改所有调用点**：如果多个地方调用同一函数，只在出问题的调用点打补丁，
其他调用点照样坏。**在共享函数里修一次，是所有调用点的最小修复。**

## 第五步：验证修复

不要凭空验证。**先拿第 0 步的复现条件重跑，必须看到它失败** ——
没失败就说明你修好了但没复现过，或者复现条件记错了。
不先看到 fail，就无法区分"修好了"和"根本没坏过"。
改完再看它变 pass，三层都要过：

| 层 | 查什么 |
|---|---|
| **修好了** | 复现路径不再报错，输出正确 |
| **没修坏** | 相关正常路径仍正常（回归） |
| **边界还在** | 边缘输入（空值/超大值/并发/重复提交）没引入新洞 |

确认无误后再删调试日志。

## 排查完：写进 .brain/

**这一步是 `abs-` 前缀的意义 —— 排查的结论不写下来，下个会话会重踩同一个坑。**

```bash
abs note "一句话结论" --when "什么时候该看这条"
```

值得写的（**能从代码 grep 到的不写**）：

| 写什么 | 例 |
|---|---|
| **假象的根因** | "报错位置是 A，真因在 B 的写入侧" |
| **判据** | "统计硬切率 >30% 即确诊，别去调 prompt" |
| **反直觉处** | "慢的不是读写，是 node 启动" |
| **排查路径** | "先查写入侧，别先怪模型" |

不值得写的：报错原文（日志里有）、修好的代码（git 里有）、通用常识。

**如果是反复踩的坑**，排查结束后提成硬规则：

```bash
abs rule add "靠提醒才能工作的功能，该删不该补"
```

## 常见陷阱

| 陷阱 | 正确做法 |
|------|----------|
| 凭经验猜位置 | 先复现 + 看日志/打印 |
| 只看代码不运行 | 打印运行时的实际数据 |
| 一次改很多地方再测 | 改一处、验证一处 |
| 修症状不修根因 | 追问"为什么这层数据变了" |
| 只验证出错路径 | 复现 + 回归 + 边界 |
| 忘记删调试代码 | 确认后清理所有打印 |
| 只在本地验证 | 确认部署的代码/数据一致 |
| 偶发当成必然 | 先找触发模式，别用单样本下结论 |
| 排查完不落盘 | 提一条 `abs note`，反复踩的提 `abs rule` |

## 兜底：卡住时

排查 >20 分钟没进展，不硬扛，回流程检查：

1. **Bug 描述还准吗？** 新观察是否改变了问题定义。
2. **复现还稳定吗？** 换个触发样本还出现吗。
3. **漏看日志了吗？** grep 全量（不只最近的），可能早期就报过错。
4. **改动范围查全了吗？** 只看 HEAD~3 会漏分支合并、配置、部署差异。
5. **要不要问人？** 这条功能最近谁改的、意图是什么，可能一句话点醒。
6. **向上游看一层。** 来源方是否也变了，不只是消费方的问题。

## 收尾：结论要明确

**不许**："可能是 X，也可能是 Y，建议排查一下" —— 这是把判断推回给用户。

**必须**给出：

1. **当前结论**（是什么 / 或"未定位"）
2. **置信度与依据**（哪来的证据 / 还是只是推测）
3. **下一步具体动作**（跑什么、看什么、要用户提供什么）

"未定位"是合法输出，但必须配一句"**需要你提供 X**"（具体到要什么），
不能只说"无法确定"就结束。

> 与第 -1 步同一根因：**模糊化是逃避判断。** 要么给结论 + 依据，要么明确索取证据。
