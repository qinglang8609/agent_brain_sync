# 架构：三层分工

> 状态：定稿（2026-11-18）。实现代码尚未开始，本文是写代码前要先钉死的边界。

一句话：**调度规则是我们的系统，角色是谁是 pi 的事。**

## 三层

| 层 | 位置 | 里放什么 | 依赖 | 谁改 |
| --- | --- | --- | --- | --- |
| **系统层（全局功能）** | `code/multi-agent/` | 共享看板的格式与读写、接力状态、`@` 门禁、收敛判定、轮次与长度上限、角色能力卡的解析 | **不 import 任何 pi 包**，`node:` 内置之外零依赖 | 我们 |
| **插件层（pi 宿主实现）** | `agents/pi/` | pi 扩展入口、`@` 解析、群聊 TUI、调 pi-subagents 的 RPC、指挥文档 SKILL.md | 可以 import pi，可以 import 系统层 | 我们 |
| **角色定义** | 项目 `.pi/agents/<角色>.md` | 每个角色一个 md：名字、一句话能力标签、工具白名单、私有记忆 | 纯 markdown，交给 pi-subagents 发现 | 用户 |

外加一份**运行时数据**：项目 `.pi/agents-chat/board.md`（共享看板，见 `board-format.md`）。

## 为什么这样切

**系统层不碰 pi**，因为它管的是「谁该说话、说话算不算数、什么时候停」——这些规则跟宿主无关。
放在纯逻辑里，可以徒手跑测试：给它一块看板和一个主持人的决定，断言它接受还是拒绝、该不该停。
出问题时能分清是**规则错了**还是**pi 集成错了**，这两类 bug 的排查方式完全不同。

**角色定义不进代码**，因为角色是内容不是程序。加一个「安全工程师」应该只写一个 md，
不该改代码、不该发版。pi-subagents 本来就按目录发现角色（`builtin < package < user < project`），
顺着它的机制走，别另造一套。

**插件层只做翻译**：把系统层的决定变成 pi 的实际动作（拉起哪个子代理、把哪段文字塞进对话），
把 pi 的事件变成系统层的输入（谁刚说完话、`@` 了谁）。

**判据只有一条**：这段代码换个宿主还能用吗？能 → `code/`，不能 → `agents/<宿主>/`。
接力状态机、看板格式、门禁判定换个宿主照样成立，所以进 `code/multi-agent/`；
扩展入口、TUI、skill 文档是 pi 的机制，所以进 `agents/pi/`。

## 数据流：一次 `@` 的完整链路

```
你: @架构师 我要做登录功能，聊聊方案
   │
   ├─ 插件层：解析出 [架构师]，查它在不在场（系统层 gate 判定）
   │        不在场 → 拒绝，提示「先用 /agents 召集」
   │
   ├─ 系统层：board.addMember('架构师') + board.setTask('做登录功能')
   │
   ├─ 插件层：调 pi-subagents RPC 拉起「架构师」这个角色
   │        上下文 = 看板快照（总任务 + 分任务 + 在场成员 + 最新动态）
   │
   ├─ 角色产出意见 → 插件层拿到结构化结果
   │
   ├─ 系统层：board.addTurn('架构师', 意见)；relay.next() 判定下一位 / 是否收敛
   │        判定依据见 relay-rules.md
   │
   └─ 循环，直到收敛 → 主持人汇总给你
```

## 不做什么

这几条在需求阶段就拍板了，别在实现时松口：

- **不造执行引擎**。角色就是 pi-subagents 的子代理，能力是 pi 工具集的子集，不另接模型、不另起进程。
- **不做角色间对等通信**。pi-subagents 的通信是树状（父↔子），强行做对等要么绕过它的 API，要么自己造消息总线。我们的做法是**主持人转发**：角色之间靠共享看板互相看见，靠主持人接力传递。
- **不替主持人做判断**。系统层只给边界（能点谁、还能几轮、算不算收敛），点谁是主持人的事。
- **不把角色写进代码**。角色是 md 文件，不是数组常量。
