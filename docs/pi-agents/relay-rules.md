# 接力与收敛规则

> 状态：定稿（2026-11-18）。硬判据落到 `code/multi-agent/relay.js` 与 `gate.js`，软判据靠主持人的 SKILL.md。

这套系统的难点不是「怎么让子代理干活」（pi-subagents 已经解决），而是「怎么让它们轮流说话、
什么时候停」。本文定的是**边界**：谁能说、能说几轮、什么情况必须停。

## 一、谁能开口：@ 门禁

三道门，从硬到软：

| 门 | 实现在哪 | 作用 |
| --- | --- | --- |
| 名单 | `code/multi-agent/gate.js` | 没被 `@` 过的角色**不在场**，主持人派发会被拒 |
| 工具 | 角色 md 的 `tools` 白名单 | 在场但没能力，也做不了超出边界的事 |
| 提示 | SKILL.md | 让主持人自己知道「没点的不能点」 |

**规则**：

- 用户 `@A` → A 进场，写进看板「在场成员」
- 主持人**不能自己召集**新角色。它想多听一个意见时，只能说「建议 @测试 一起看」交给你决定
- 唯一的例外：你说「召集所有人」或「@all」→ 全部角色进场，仍要各自被点名才发言
- 一次最多 4 个角色在场。超了先劝退（把不在场的角色从名单里去掉），不加人

**为什么门禁要在系统层判，而不是靠 prompt**：靠 prompt 就是靠自觉，角色一多必然有越界的。
而名单判定是一行代码，判错了能测出来。

## 二、主持人怎么点下一位

按优先级，命中即停：

1. **上一轮有人点名让谁接** → 点它（尊重角色之间的委托）
2. **出现实现问题**（「能不能引这个依赖」「这个接口怎么定」）→ 程序员
3. **出现风险或异常路径**（「过期怎么办」「安全」「没测过」）→ 测试
4. **出现取舍问题**（「要不要做」「值不值」）→ 产品
5. **以上都没有新角度** → 收敛

**限制**：

- 每轮默认只点 1 个。你明确说「多听几个意见」才点 2 个，上限就是 2
- 不连续两轮点同一个角色（除非它上一轮提的问题被别人答了、需要它确认）
- 同一个角色连续两次说「同意」而没有新内容 → 视为终结，不再点它

## 三、轮次与长度

| 项 | 默认 | 可由谁调 | 超了怎么办 |
| --- | --- | --- | --- |
| 接力轮次 | 3 轮 | 用户在会话里说「再聊两轮」 | 强制收敛，输出汇总 |
| 在场角色 | 4 个 | 用户 `@` 决定 | 拒绝进场并说明理由 |
| 单轮意见 | 300 字 | 不改 | 主持人压缩后再写入看板，原文丢弃 |
| 看板动态条数 | 12 条 | 不改 | 旧的压成一行摘要（见 `board-format.md`） |

**为什么单轮要限 300 字**：看板是每轮都要塞进所有在场角色上下文的东西。四个角色 × 八百字 ×
三轮 = 一万字起步，一半是重复。限制长度不是省 token，是逼意见收敛。

## 四、收敛判据：双保险

硬判据（系统层判，任一命中就停）：

- 轮次到上限
- 连续 2 轮没有新增「分任务」或「风险条目」（说明讨论在原地打转）

软判据（主持人自己喊停）：

- 角色开始重复自己或别人说过的话
- 话题跑到总任务之外
- 只剩「同意」「好」这类附和

**谁说了算**：硬判据命中必然停，主持人无权延长；软判据由主持人判断，但**必须说明停的理由**
（哪句开始重复、哪里跑题），并且这句理由要写进最终汇总。

**收敛后必须产出**：结论（1-3 条）+ 分工（谁做什么）+ 未决问题（需要你定的）。三者缺一，
这次讨论就等于白聊。

## 五、中断与失败

| 情况 | 处置 |
| --- | --- |
| 子代理超时或报错 | 看板记一行「X 未应答」，**不重试同一个角色**（重试大概率还是同一个错） |
| 用户中途插话 | 立即停掉当前接力，按新指令走 —— 不排队、不把剩下的话说完 |
| 用户按 ESC 中断 | 已写入看板的动态保留，下一轮从断点继续 |
| 角色产出了空内容 | 记「X 无新意见」，算作一次收敛信号 |

**为什么失败不重试**：接力是有成本的（时间 + 模型额度），而且同一个角色失败两次通常是
配置问题（tools 给错了、模型不可用），重试不解决。报告出来让人看。

## 六、聊天与干活分离

两个阶段，不要混：

**阶段一：聊**（本系统的主场）

- 所有人都**只发表意见**，不动手
- 产出：结论 + 分工 + 未决问题
- 这一阶段的目标是「想清楚」，不是「做出来」

**阶段二：干**（交给 pi-subagents 原来的模式）

- 主持人按分工并行派发子代理去实现
- 能动手的只有程序员（以及你在角色 md 里明确给了写权限的角色）
- 产出：改动 + 验收结果

**为什么必须分开**：边聊边改，讨论还没定就开始改代码，改错了要回滚，回滚完讨论也乱了。
而且聊天阶段全给只读工具，是能力边界最省的实现方式 —— 不用靠「请勿动手」这种劝告。

## 七、一句话总结

**用户点名决定谁在场，主持人决定谁接话，硬上限决定什么时候停。** 三层各管一段，
互不越界 —— 这样出问题时能立刻定位是哪一层的锅。
