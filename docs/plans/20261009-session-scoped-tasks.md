# 方案：todo 行标会话 id —— 塞进已有的 `(认领 …)` 字段

日期：2026-10-09
状态：**已落地，565 测试全过**

## 0. 需求（三轮澄清后的最终形态）

### 用户原话

> 当一个项目 开两个 pi 或者两个 opencode，他们都的 todo 是一样的，这就导致了 a 再进行任务 test
> B 也能读到 test 并开始执行，任务串了。要求是：每个 pi 能知道自己进行的任务，
> 哪些是自己的，哪些是人家的，哪些在进行中，哪些没有进行 等待执行。

### 纠错一：不是硬隔离

> 不是的 咱们是改 todo 啊 让 llm 知道 todo 这个条是哪个会话的就行
> **不属于我的会话的 就别乱进行，但是用户强制要进行 那也得接手**
> id 是跟着 todo 的，todo 归档到 sessions 后 也要跟着，这样 做的事情就有迹可循了

### 纠错二：不要信标体系

> 1 接手要提示
> 2 **sessions 里面只放了 todo 的归档，再放进去 `<sid>.md` 不就乱了** ——
>   我的意思是 在 todo 上标记 sid 之后 正常归档到 sessions，
>   **能看到每条任务的会话 id 就可以，不是给每个会话都留 `<sid>.md`**

### 纠错三：sid 让 LLM 自己给

> sid 让 llm 自己给答案吧

### 最终形态

| # | 需求 | 落地方式 |
|---|---|---|
| 1 | todo 行标 sid，LLM 自己判 | 行尾 `(认领 日期 <sid>)`；hook 把本会话 sid 摆进 system prompt |
| 2 | 用户强制要做 → 能接手 | 另一个 sid `start` 直接覆盖（**不拦截**） |
| 3 | 归档后 sid 跟着 | 塞进已有字段 → **整行搬运自动兼容，零改动** |
| 4 | sid 让 LLM 自己填 | 不搞进程探测；hook 注入 sid，LLM 登记时传 `--session` |

## 1. 核心设计：复用 `(认领 …)`，不新增字段

```
登记: - [ ] [进行中] T1 [[fanchao]] — 描述 (认领 2026-10-09 01a11eae)
                                        ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ 日期 + sid
完成: - [x] T1 [[fanchao]] — 描述 【落地】 (完成 2026-10-09 01a11eae)
```

**为什么复用而不是新增字段**（这是本方案最省的一点）：

| 已有机制 | 复用的效果 |
|---|---|
| 归档是**整行搬运** | sid 自动跟着进 `sessions/` —— 需求 3 **零改动** |
| 6 处解析里 5 处用 `\(认领[^)]*\)` **通配** | 加 sid 后自动兼容 —— 只需改 1 处 |
| `(认领 日期)` / `(完成 日期)` 已同族 | 排版一致，好读 |

## 2. 实测：6 处解析，只有 1 处要改

| 位置 | 正则 | 带 sid 后 |
|---|---|---|
| `common.js` extractNote | `\(认领[^)]*\)$` | ✅ 自动兼容 |
| `common.js` isPlaceholder | `\(认领[^)]*\)` | ✅ 自动兼容 |
| `store.js` done 剥离 | `\(认领[^)]*\)` | ✅ 自动兼容 |
| `wrapup.js` ×2 | `\(认领[^)]*\)$` | ✅ 自动兼容 |
| **`hooks/abs.pi.ts` 看板解析** | `\(认领\s*\d{4}-\d{2}-\d{2}\)$` | ❌ **写死日期格式，必须改通配** |

**只有 hook 那处**（`parseOpenTasks` 的 desc 提取）需要改，因为它是唯一写死格式的。

### 3.1 LLM 怎么拿到 sid（用户方案：让它自己给）

hook 在 `before_agent_start` 把 sid 摆进 system prompt：

```
[会话] 本会话 id = 01a11eae。登记任务时带上它（abs todo start <id> --session 01a11eae），
任务行尾会记成 `(认领 日期 01a11eae)`，这样多会话并行时能看出哪条是谁在做。
```

- **不搞进程探测**（MCP 拿不到 pi 的 sessionId，为此要建运行态文件 + ppid 反查——太复杂）
- **取不到 sid 就不注入**（不写空值、不伪造）

## 4. 明确不做（用户否掉 / 我评估后砍掉）

| 不做 | 原因 |
|---|---|
| ❌ `.brain/sessions/<sid>.md` 信标 | 用户：会污染 todo 归档区 |
| ❌ `kill(pid,0)` 判会话死活 | 用户：不区分，只标 sid |
| ❌ 隐藏别人的任务描述 | 用户要看得见才好判断（藏了反而导致接手时不知道干什么） |
| ❌ 自动认领 | 守 `remind-vs-gate` 铁律（12 次失败换来的） |
| ❌ 新锁 | 本次是重复执行，不是写冲突 |
| ❌ MCP 沿 ppid 反查会话 | 用「LLM 自己给」替代，省掉整套运行态文件 |
| ❌ 各文档 frontmatter 加 `session:` | 先跑通 todo 这条链；扩展是后续 |

### 5.1 端到端实测（手工跑的）

```
登记:   - [ ] [进行中] T1 [[fanchao]] — 带会话 (认领 2026-10-09 01a11eae)
不带:   - [ ] [进行中] T2 [[fanchao]] — 无会话 (认领 2026-10-09)      ← 旧格式不变
重复:   - [ ] [进行中] T1 [[fanchao]] — 带会话 (认领 2026-10-09 01a11eae)  ← sid 保住
接手:   - [ ] [进行中] T1 [[fanchao]] — 带会话 (认领 2026-10-09 01a11f2a)  ← 换成新 sid
完成:   - [x] T1 … 【落地】 (完成 2026-10-09 01a11eae)                ← 带进 Done
归档:   sessions/log-2026-01-01.md 里 - [x] T1 … (完成 2026-01-01 01a11eae)  ← 跟着走
```

### 5.2 途中修的一个真 bug

`done` 原本把整段 `(认领 …)` 删掉换成 `(完成 日期)` —— **sid 会丢**。
而「已完成的任务是谁做的」恰恰最常被回查。
修法：`done` 时用 `sessionOf(l)` 取出 sid 带进 `(完成 日期 sid)`。

## 6. 认领 ≠ 完成（2026-10-09 用户追问后补）

### 问题

用户问：「如果 认领是 a 完成是 b 呢」。

实测第一版的行为 —**错的**：

```
A 认领: - [ ] T1 [[fanchao]] — A 做的 (认领 2026-10-09 01a11eae)
B 完成: - [x] T1 [[fanchao]] — A 做的 — B 收尾 【落地】 (完成 2026-10-09 01a11eae)
                                                        ^^^^^^^^ 这是 A，不是 B
```

原实现把**认领者的 sid 原样搬进 `(完成 …)`** ——
「完成时间」配着别人，语义拧，而且 B 根本不畘痕迹。

### 规则（用户定：两个都留；同一个则只写一个）

| 情形 | 行上写成 |
|---|---|
| A 认领，B 完成（不同会话） | `(认领 日期 A) 【落地】 (完成 日期 B)` |
| A 认领，A 完成（同一会话） | `(完成 日期 A)` —— 不重复写两遍 |
| A 认领，done 未给 sid | `(完成 日期 A)` —— 沿用认领者，不凭空编 |
| 无认领，B 完成 | `(完成 日期 B)` |
| 都无 | `(完成 日期)` —— 旧行为 |

### 实现

- `markDone(file, id, kind, conclusion, bySid)` —— 新增 `bySid` 参数（完成者）
- `cmdTask` 的 done 分支把 `sid` 传给 `markDone`
- 判断 `claimSid !== doneSid` 决定要不要额外留认领段

### 实测五种情形

```
A认领/B完成: - [x] T1 … (认领 2026-10-09 01a11eae) 【落地】 (完成 2026-10-09 01a11f2a)
A认领/A完成: - [x] T2 … 【落地】 (完成 2026-10-09 01a11eae)
done无sid:   - [x] T3 … 【落地】 (完成 2026-10-09 01a11eae)
无认领/B完成: - [x] T4 … 【落地】 (完成 2026-10-09 01a11f2a)
归档后:      两个 sid 都完整保留 ✓
```
