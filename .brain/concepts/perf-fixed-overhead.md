# 性能优化：先分解固定开销，再决定优化哪一段

## 触发场景
「每次读写都很慢」→ 直觉反应是「优化读写逻辑」或「换更快的存储/语言」。
**这个直觉通常是错的**：慢的往往不是你以为的那一段。

## 实测：abs 单次命令 27ms 的构成

```
node 空跑              : 20 ms   ← 进程启动（固定开销）
node 只 import 模块     : 24 ms   ← + 模块加载 4ms
node + import + 真实调用 : 27 ms   ← + 真实读写仅 3ms
```

**结论：读写只占 3ms，固定开销占 24ms（89%）。**

同样的逻辑用「单进程内重复调用」验证更干净：

| 方式 | 单次耗时 |
|---|---|
| 每次独立起进程（CLI 现状） | **28.8 ms** |
| 单进程内重复调用（纯读写） | **0.2 ms** |
| 空 node 启动（啥也不干） | 21.9 ms |

**进程启动占 99%。**

## 关键推理：哪些开销「可消除」？

这是最容易搞错的一步。**不是测量出来的大头都能优化掉。**

以本项目的 daemon 方案为例：常驻进程把「读写」从 7ms 降到 2ms，但：

```
CLI 无 daemon : node启动20 + 读写7  = 27ms
CLI + daemon  : node启动20 + 读写2  = 22ms   ← 只省 5ms
MCP  (常驻)   : 0        + 2        = ~2ms   ← 唯一能消掉20ms的路径
```

**因为 `abs` 本身是 node 脚本 —— 只要走 CLI，那 20ms 启动就逃不掉。**
daemon 优化的是「读写」，而读写从来不是瓶颈。

**教训**：我最初把 22ms 全当作「可优化项」，实际只有 7ms 可动。
**必须逐段追问「这一段在我的调用路径上，是否真的能被拿掉」。**

## ✅ 分析步骤（可复用）
1. **测空转**：跑一个啥也不干的同构调用（`node -e ""`）—— 这是不可压缩的地板
2. **测分段**：空转 / 只加载 / 加载+真实执行，差值即各段成本
3. **标出不可消除项**：由调用形态决定的固定成本（如 CLI 必然起进程）
4. **只优化剩余部分**；若剩余部分很小 → **别优化**，换调用方式更快
5. **收益 vs 复杂度**：为 <10ms 收益引入常驻进程/新语言/新依赖，通常不划算

## 决策留档：daemon 方案被否（2026-09-10）
已实现并跑通（socket 直连 0.40ms、冷启自动拉起 74ms、`stop` 清理干净），
但**实测收益仅 27→22ms，最终撤掉**。理由：
- 收益边际（省 5ms），代价是常驻进程生命周期（崩溃恢复/残留 socket/跨平台差异）
- 真正的瓶颈是**行为**（agent 一轮发多条命令），不是单次成本 → 该用规则约束
  （写操作走 MCP，单次 ~2ms），而非加进程
- 判据：**为 <10ms 收益加一个常驻进程不划算**
