# 话题树两态模型

## 结论

`## Topics` 不是**另一份记录**，是「同一件事」的**入口态**。话题成熟后**移动**
（`abs topic promote #N`）进 `Today`，保留同一个 id，一路追到 `Done`。

```
话题产生 → Topics(进行中) → promote → Today → done → Done
             ↓ 否决/结论
          离树，结论落 sources/
```

**关键判据**：讨论与执行是**同一件事的两态**，不是两条线索。复制两份会出现
「树上一条、看板一条、Done 又一条」三份互不相干的记录，谁也追不到谁。

## 为什么不是「提醒 AI 更勤」

**记录率 7% 的真因是触发频率，不是 AI 偷懒。**

`abs` 原本只有 `agent_end` 一个触发器，而话题是会话中途**连续产生**的事件。
用一次性提醒追持续事件，必然漏掉绝大部分 —— 这不是提醒写得不够啰嗦能解决的。

修法是**增加触发锚点**（见 [[session-material-accumulation]]）：
- 用户发话 = 天然话题边界（`before_agent_start`）
- 每轮结束 = 机械事实（`turn_end`）

## 分层（不要混淆）

| 轨道 | 位置 | 放什么 | 时间尺度 |
|---|---|---|---|
| 讨论 | `## Topics` | **只放 `进行中`** | 此刻 |
| 执行 | `Backlog`/`Today`/`Blocked`/`Done` | 要动手的事 | 当下 |
| 铁律 | `## Rules` | 违反会丢数据的 | 恒定 |

**五态（已结论/已否决/已落地/未落地/待验证）一律离树** —— 树的价值是「当前在哪」，
死话题会把活话题淹掉。离开前结论**必须**落 `sources/`（`abs note`），否则就丢了。

`未落地`/`待验证` 也离树，因为它们的真实语义是**暂停**（等人/等数据），
应作为任务追踪（Blocked），不是「正在讨论」。

## 读取侧约束

**`abs load` 只打印一行 Current（`⌖ #1 根 › #1.1 子`），不打印整棵树。**

整棵树被反复读会**带偏后续会话**——这是 `## Roadmap`（2026-09-13 已删）同一个病：
AI 写的总结被读回，下个会话当成"当前状态"照做。全貌用 `abs topic` 主动查。

## 出处

2026-09-13 与用户讨论确立。用户原话：「会话产生话题 → 记录话题 → 否定了就删除，
过程中发现新话题记录新话题…确定了写入 Today，开发完成的进 Done」。
