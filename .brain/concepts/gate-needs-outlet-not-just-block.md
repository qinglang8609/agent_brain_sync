# 概念：加闸门必须同时给出路，否则污染会换形态复发

## 触发场景

某处被反复塞进不该有的内容（`todo.md` 里堆实施报告、issue 里堆日志、配置里堆注释），
于是加校验拦住它。**如果只拦不给替代落点，同一个问题会以新形态复发。**

## ❌ 表现

`todo.md` 的「总结污染」在 2026-10-05 → 10-11 之间复发了**三次**：

| 次数 | 拦的方式 | 下一次的绕过 |
|---|---|---|
| 1 | 断点 > 200 字 → 拒 | 写短一点、多写几行 |
| 2 | 断点 > 2 句/带列表 → 拒 | **不写成断点**，改成裸文本行 |
| 3 | （白名单闸门，见 [[validation-gate-on-shared-write-path]]） | —— |

第 3 次修完（白名单），用户仍然说「**又**出现这个问题了」。而且清理时的 commit
信息露了底：**「原内容只存在 todo.md，删任务时差点永久丢失」**。

这句话是关键——**那些「乱七八糟的总结」不是凭空产生的噪音，是真实数据**。
只是它当时没有别的地方可去，就被顺手搁在 todo 里了。

所以真正的根因不是「闸门不够严」，而是**缺一个落点**：

| 想记什么 | 当时有什么 | 合适吗 |
|---|---|---|
| 下一步做什么、卡在哪 | `↳ 断点` | ✅ 合适，但**只能一句话** |
| 干活途中的发现/取舍/测试数据 | `abs log` | ❌ 要起 kind、进 log.md，对「随手记」太重 |
| 提炼过的经验/坑 | `abs note` | ❌ 只管经验，且落 sources/ |

中间那一档（「任务内、多句、不定长、随手写」）**不存在** → 只能塞 todo。

## 🛠 解法

**加闸门时，先问「被拦的内容该去哪儿」，把那条路修好再拦。**

这一条比判据本身更重要：判据说的是「不许往这放」，落点说的是「往那放」。
只有前者，写入方要么卡住、要么换个写法再塞。

具体到 todo 随手记（`abs todo memo`）的设计，四条判据：

1. **落点复用已有目录，不新建**：放 `sessions/`（已有目录遍历/frontmatter/归档机制），
   靠现成的 lint 豁免判据过关，**零契约改动**：
   - `archive` tag → `SESSIONS-SPLIT`/`SESSIONS-NAMING` 豁免（它们只统计无 archive 的）
   - `log-` 前缀 → `ORPHAN-PAGE` 豁免
   - 但 `INDEX-MISSING` **不会**自动豁免 → 初版实测被报，加 `task-memo` tag 豁免
     （随手记是过程草稿，数量随任务增长，登记会冲垮 index）
2. **与相邻档位语义要有区别**，否则会互相顶替：
   - 断点 = **覆盖式**（「现在到哪了」，旧值就该被替换）
   - memo = **追加式**（「过程流水」，旧值不能丢）
3. **不上主界面**（用户明确要求）：随手记占的不是看板空间，去看板就毁掉「看板 = 任务清单」的契约
4. **任务结束后不丢**：随 `sessions/` 留存（正面回应上面那句「差点永久丢失」）

## 验证

- 真机走完一轮：`memo` 追加两条（含超长多句）→ 看板仍只有一行 → `lint` 0 问题
- 任务 `done` → 笔记文件仍在 `sessions/` 且可读回
- `archive` 迁走旧 Done 组 → 笔记文件与 `log-<日期>.md` **共存**，lint 仍 0 问题
- 破坏验证：注入「id 后缀匹配」→ 前缀污染测试红；注入「首建绕过锁」→ 并发丢条目测试红
