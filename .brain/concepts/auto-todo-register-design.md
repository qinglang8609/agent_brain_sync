# 自动登记 todo 的失败复盘：三次迭代后整体移除

## 触发场景
「任务登记不及时、换会话断点丢失」。**先试过 system prompt 常驻指引**
（promptGuidelines，实测 414 次有痕），行为没变 —— 因为指引假设 agent 已决定
"要开一个任务"，而排查类工作没有清晰的开工时刻（"我先看看怎么回事"，
看明白了活儿已干完一半）。于是改成 **hook 替 agent 登记**，做了三版。

## 🛠 三版迭代（每版都被用户实报打回）

| 版本 | 做法 | 用户实报 |
|---|---|---|
| 1.14.0 | 一按回车就登记 + `auto-<会话uuid>` 当 id | —（初版） |
| 1.14.1 | 挪到"第一次真改文件"才登记 | 名字抽成开场白（`我已经重启测试一下`） |
| 1.15.0 | 改 TBD 占位 + 新增 `abs todo rename` | 卡顿 + 看板堆满 `auto-TBD-xxx 待命名` |
| **1.15.2** | **整体移除** | — |

## ⚰️ 最终为什么删掉

两条实报，都是自动化本身造成的：

1. **卡顿** —— `agent_end` 每轮 spawn 一个 node 进程。当时的守卫写的是
   `if (!brain || !autoTaskSeen) return`，但 `autoTaskSeen` 一旦置位就**永远为 true**
   → 之后**每个 turn 结束**都起一个进程（纯对话轮也不例外）。用户直接感觉到卡。
2. **看板被占位堆满** —— 占位条目**直接写进看板**，而用户大多不会去改名
   → 一堆 `auto-TBD-xxx — 待命名` 比不登记还糟。

## 🧠 真正的教训（比"参数调不准"更根本）

**三次都在试图让机器做需要理解的事：**

- 替 agent 决定"这是件事" → 判据永远不准（"一按回车"太早、"真改文件"仍不准）
- 替 agent 起名字 → 只能抽字面，抽出的是 `我已经重启测试一下`（开场白）；
  退而用断点兜底 → `本轮有改动`（**hook 自己生成的文本**，等于把机器的话当用户意图）
- 替 agent 记断点 → 每轮起进程，白烧

**而用户真正想要的名字（`fix-skill-trigger` / `fix-opencode-v2-plugin`）
不是抽出来的，是理解「在干什么」之后起的。**

> **通则：自动化必须挂在"机器确实知道"的判断上。**
> hook 知道「动过文件了」，不知道「这是件什么事、该叫什么名」——
> 后者需要读懂上下文，那是 agent 的活。硬让 hook 猜，产出的东西没人能用。
>
> 与项目 Rule「靠提醒才能工作的功能，该删不该补」同源：
> **"提醒"和"自动替你做"都是同一个错 —— 让不掌握判据的一方去启动动作。**

## ✅ 最终形态（v1.15.2）

| 环节 | 谁做 |
|---|---|
| 判断"这是不是一件事" | **agent**（读懂了才知道） |
| 起名字 | **agent** |
| 写看板 / 记断点 | **agent 主动调 `abs_task`**（它本来就在跑，不额外起进程） |
| hook 侧 | 只留一行可观测痕（`tool_call first_write`），**不写盘、不起进程** |

保留的通用能力：`abs todo rename <旧id> --note "<新id>"`（改名，描述同步换掉）。

## 顺带留下的可复用判据（未删的逻辑本身有价值）

即使功能删了，这些判据在别处仍适用：

- **写类工具白名单必须含 bash**，且 bash 要额外甄别（`>`、`sed -i`、`tee`、`rm`…），
  否则 `ls`/`git status` 也算"干活"（见 [[opencode-inject-channel-verdict]]）
- **问句不算指令**：`为什么/怎么/能不能/…吗` 要过滤 —— 提问不是让动手
- **幂等键与展示名要分开**：机器用的键（会话 id）藏进标记，给人看的 id 另设
- **收尾清理不能按 id 前缀认领**：人工也可能起 `auto-fix-x`，要按专属标记认
