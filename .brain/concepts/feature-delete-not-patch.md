# 功能该删不该补：触发频率是设计错误，不是实现错误

## 触发场景
新功能「加了但不生效」或「太吵」时，第一反应想去**修它/加提醒**。
本仓 2026-09-13~15 连续四次踩同一类，全部正解都是**删**。

## ❌ 表现：三种反复出现的失败模式

| # | 症状 | 当时的错误反应 | 正解 |
|---|---|---|---|
| 1 | 话题树 `## Topics` 没人用（Backlog/Today 常年 0 条） | 调结构、加状态 | **整个删掉** |
| 2 | 写文件即弹 Follow-up（每轮都弹，满屏） | 加节流守卫 → 修守卫 | **整个删掉** |
| 3 | todo 自动登记不生效（写文件不登记） | 在 agent_end 加提醒 | **换触发时机，不加提醒** |
| 4 | `abs pages` 复刻 `abs index`（38 页全列，上限一次没触发） | 保留（"以后可能有用"） | **删掉** |

## 🛠 根因（三条，互相独立）

**① 触发频率错 = 设计错误，修实现救不了**
失败模式是「任务从开始到完成都在同一会话内走完，中间那个『挂到进行时分区』的动作既来不及也不需要」
（话题树）—— 这是**工作流不匹配**，不是 bug。改实现只会把错的设计做得更顺。

**② 只有一个触发器、且判据过粗 → 机会全丢**
`abs` 当时只有 `agent_end` 一个触发点，还被 `loggedToday`（整天闸门）卡死。
用户已想结束、AI 只想收尾时提醒登记 → **必被忽略**。
→ 正解是**换触发时机**（写文件时），而不是**加提醒强度**。（换时机后 1.8.0 仍失败，
最终连功能一起删 —— 见下"判据"。）

**③ YAGNI：从别人架构图推出来的功能不是需求**
`abs pages` 的来历是"看别的项目有 manifest，所以我们也该有"。
判据：**它和已有 `abs index` 功能重叠**（38 页全列），复用即有零维护成本的替代。

## 🛠 判据（可执行，不必凭感觉）

1. **它和已有功能重叠吗？** 重叠 → 复用/删，别新增（`abs index` 已给全量清单）。
2. **触发时机对得上真实工作流吗？** 「用户已想结束时提醒他登记」= 时机错，改时机不是加提醒。
3. **"以后可能有用"是需求吗？** 不是。没有当下触发它的真实场景 → 删。
4. **删比修贵在哪？** 一般更便宜：删掉的是维护成本 + 认知负担 + 每次触发的噪音。

## ⚠️ 反面：靠提醒才能工作的功能，该删不该补
本仓已升为硬规则。判断口诀：
**若这功能需要"记得去用它"才能生效，它就已经死了 —— 别给它加提醒，删了它。**

## 🛠 已验证的落地形态（经验生命周期）
「只写不删」也是同一类病：原先 9 条 source 全部没提炼、推翻一条只能 `rm` 文件。
→ 改为 **`status` 三值（active/draft/superseded）+ `abs supersede`**：
**推翻不删页**（删了会让下个会话重踩同一个坑、重新记一遍），只改一行标记。

## 验证命令
```bash
# 检查是否又长出"重叠功能"
abs index | wc -l        # 清单类命令是否重复提供同一份信息
# 检查经验是否可回退（不该只能 rm）
abs query <词> --all     # superseded 是否默认隐藏且可查回
```
