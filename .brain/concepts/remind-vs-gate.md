# 概念：todo 对齐机制 —— 对齐是必须的，门禁是兜底

## 触发场景
要治「LLM 干活不及时更新 todo」「某个动作 LLM 总忘记做」「想加个提示让 AI 记得 X」
—— **任何"希望 LLM 养成某个习惯"的需求**。先读这页，别再走一遍。

## ❌ 表现
看板与真实工作**脱离**：干了活没登记、登记了没结项、看板上挂着「进行中」但活早干完了。
实测量化（2026-10-05）：**一晚 18 个 git 提交，只有 3 条 todo 记录**。

用户原话：「todo 与你做的事情脱离」。

## 🛠 解法

### 结论（2026-10-05，12 次尝试后，用户定的两层）

> **① 对齐是必须的 —— 每步都要做。
>  ② 门禁是兜底 —— 漏了也跑不掉。**

**不是二选一，是主 + 备：**

| | 角色 | 管什么 | 装在哪 |
|---|---|---|---|
| **对齐** | **必须**（每步） | 让 LLM **看得见**看板 | `before_agent_start` 把看板拼进 system prompt |
| **门禁** | **兜底**（漏了才兜） | 漏了也**跑不掉** | `pre-commit` 对比「代码变了 vs 看板没变」 |

**为何必须是两层**：对齐解决「看不见」，但它**做不到**让 LLM 主动登记
（实测三次给活、主动登记 0 次 —— 看得见 ≠ 会去做）。
门禁补的正是这一段：不管 LLM 有没有想起来，**提交时必被摆到面前**。

### 12 次尝试里什么是死的、什么是活的

|---|---|---|---|
| 1 | v1.8.0 | 写文件就自动提醒 | 实报「每轮弹 Follow-up」→ v1.8.1 删 |
| 2 | v1.9.1 / 1.9.4 | SKILL 开工前触发器 + 收尾注入任务优先 | 无效 |
| 3 | — | 静态指引 `promptGuidelines`（有痕 **414 次**） | 行为没变 |
| 4 | v1.14.0 | hook 一按回车就登记 | 「还没产生需求就加了」 |
| 5 | v1.14.1 | 挪到「第一次真改文件」 | 名字抽成开场白 `我已经重启测试一下` |
| 6 | v1.15.0 | auto-TBD 占位 + `todo rename` | 卡顿 + 看板堆满 `auto-TBD-xxx 待命名` |
| 7 | v1.15.2 | 整体移除（承认方向错了） | — |
| 8 | v1.16.0 | 照 rpiv-mono 重写指引（锚点提前到"收到指令"） | 当晚仍漏 |

| 12 | 2026-10-05 | **pre-commit 门禁对比** | **当晚跑 5 次，零抱怨，零漏** ✅ |

### 两类失败，一个根因

**第一类（#1-3、#8-10）「提醒 LLM」** —— 把信息摆到眼前。
共同死法：**看见了，照样不做。**

**第二类（#4-6）「替 LLM 判断」** —— 让机器猜「这是不是件事、该叫什么名」。
共同死法：**判据不在机器手里**，产出的东西没人能用（占位堆满看板）。

**根因是同一条**：

> **让不掌握判据的一方去启动动作。**
> （项目 Rule 原话：「靠提醒才能工作的功能，该删不该补；让不掌握判据的一方启动动作，同样该删。」）

### 为什么门禁有效

`pre-commit` 满足三个条件：

1. **不做就过不去** —— 提交是硬动作，不是"提醒一下"
2. **不打断对话** —— 只在 `git commit` 时（人本来就在等）
3. **只做客观对比，不猜** —— `git` 里有没有代码变更、有没有 `todo.md` 变更，都是事实

第三条是关键：**门禁不判断「这算不算一个任务」**（那是 LLM 的活），
只把「代码变了」和「看板没变」摆在一起，**逼一次显式决定**。

实现见 `.githooks/pre-commit` 末尾（约 30 行），逃生口 `ABS_NO_TODO=1`。

### 「对齐」与「门禁」的分工（别搞混）

两者都装上了，但**职责不同，不可互相替代**：

| 对齐能做到 ✓ | 对齐做不到 ✗ |
|---|---|
| 让 LLM **看见**看板现状 | 让 LLM **主动**去登记 |
| 用户提示时能**立刻接上**（不用翻文件） | 让 LLM **动手前**想起来 |
| 提供判断素材 | 替代判断 |

| 门禁能做到 ✓ | 门禁做不到 ✗ |
| 漏了也**跑不掉**（提交时必被摆出来） | 拦住「不提交就干活」的场景 |
| 不打断对话（只在 commit 时） | 判断「这算不算一个任务」（那是 LLM 的活） |

**教训**：曾因「三次没主动登记」就把 `board-align` 标成【否决】，被用户当场纠正 ——
被质疑的只是「它能不能代替 LLM 登记」，不是机制本身。
**对齐只管「看得见」，它本来就不负责「会去做」。**

### 判断该用哪一招

```
这个动作，LLM/人不做会有什么后果？
  ├─ 没后果（只是不够好）      → 别加机制。承认它靠人提一句。
  └─ 有硬后果（发错版/状态失真）→ 找那个"不做就过不去"的关卡，挂在那里
```

**可用关卡清单**（本项目已验证的）：
- `git commit`（pre-commit）← 今晚用了这个
- `git push`（pre-push，跑全量测试）
- 写入侧校验（如 `cmdRule` 拒超长 Rule、`markDone` 拒矛盾结语）

## 验证

**怎么确认「门禁真的在设计的位置生效」**（四场景双向验证，2026-10-05 实测通过）：

```bash
cd <项目根>
# ① 改了代码、没动看板 → 必须有提示
echo "// probe" >> src/text.js && git add src/text.js
sh .githooks/pre-commit | grep -c "本次提交改了代码"   # 期望 1
git checkout HEAD -- src/text.js

# ② 同时改了代码和 todo.md → 不能提示
# ③ 只改文档（README）→ 不能提示
# ④ ABS_NO_TODO=1 sh .githooks/pre-commit → 不能提示
```

**能否真改变行为的判据**（尚未验证，见看板 `board-align`）：
下次真实提交时门禁弹了提示 → LLM 是否**当场去登记了**。
成了标【落地】，没成标【否决】。
