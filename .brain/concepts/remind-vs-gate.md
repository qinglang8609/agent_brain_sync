# 概念：todo 对齐机制 —— 对齐是必须的，门禁是兜底

## 触发场景
要治「LLM 干活不及时更新 todo」「某个动作 LLM 总忘记做」「想加个提示让 AI 记得 X」
—— **任何"希望 LLM 养成某个习惯"的需求**。先读这页，别再走一遍。

## ❌ 表现
看板与真实工作**脱离**：干了活没登记、登记了没结项、看板上挂着「进行中」但活早干完了。
实测量化（2026-10-05）：**一晚 18 个 git 提交，只有 3 条 todo 记录**。

用户原话：「todo 与你做的事情脱离」。

## 🛠 解法

### 核心结论（用户 2026-10-05 原话）

> **不要试图用技术手段实现 todo。用简单的对齐，让 LLM 自己发现问题、自己反思。**

一句话分工：

```
技术只负责「摆事实」  →  看板上现在有什么、我刚刚改了什么
LLM 负责「发现与反思」→  这两者对不对得上？要不要补记/转状态/删？
```

**越界就是错**：任何“替 LLM 发现漏登记”的技术（追踪痕迹、比对差异、提醒补记）
都属于越界，已被十二次尝试反复证明失败。

### 如何做到（照 vibe-coding-help §4 数据引导论）

| # | 该做 | 本项目落地 |
|---|---|---|
| 1 | **摆事实** —— 原始数据原样摆，不替它总结 | 每轮把看板拼进 system prompt |
| 2 | **提问题** —— 用问题引注意力到具体数据上 | 那句「正在做的算哪条？有新任务要加吗？有该删的吗？」 |
| 3 | **等它自己说** —— **没说就再摆一组更窄的数据，别给答案** | 不自动登记/不追踪/不提醒。**就等着** |

**第 3 条是最难守的一条** —— 今晚就破了：摆完事实后忍不住去实现
「改动痕迹追踪 + load 显示差异」，被用户打回。

**为何不能急着给答案**：摘要丢掉的恰好是它要发现的线索；
替它下结论 = 把 LLM 的判断力废掉，而判据本来就在它手里。

### 界限（skill §4）：字符级对错照旧上代码

「不用技术手段」**仅限语义问题**。确定的对错（校验、转义、防丢数据）照旧写代码。
本项目的分例：`pre-commit` 门禁 = 字符级对比（代码变了 vs 看板没变），**保留**。

### 两层实现

> **① 对齐（每轮都摆）—— 必须。
>  ② 门禁（提交时对比）—— 兜底。**

| | 角色 | 管什么 | 装在哪 |
|---|---|---|---|
| **对齐** | **必须**（每步） | 让 LLM **看得见**看板 | `before_agent_start` 把看板拼进 system prompt |
| **门禁** | **兜底**（漏了才兜） | 漏了也**跑不掉** | `pre-commit` 对比「代码变了 vs 看板没变」 |

**为何必须是两层**：两者解决的是两件事，不能互相替代。
对齐让 LLM **每轮都看得见看板**（不用回忆/不用翻文件）；
门禁补的是「看见了也不一定去做」那一段 —— 提交时必被摆到面前。

**实测经验（别拿错尺子）**：曾用「LLM 会不会主动登记」去评判对齐，
测出三次 0 次就差点判它无效 —— **尺子拿错了**。对齐的作用是「看得见」，
不是「会去做」；实际应用里它一直在起作用（用户一提就能接上、回答基于真实状态而非回忆）。

### 12 次尝试，两类失败，一个根因

| 类 | 尝试 | 死法 |
|---|---|---|
| **提醒 LLM**（#1-3、#8-10） | 写文件提醒 / SKILL 触发器 / 静态指引(有痕 414 次) / 重写指引 / Rule 放 load 首位 / 每轮摆看板 | **看见了，照样不做** |
| **替 LLM 判断**（#4-6） | hook 一按回车登记 / 挪到改文件 / auto-TBD 占位 | **判据不在机器手里** → 产出占位堆满看板 |

**根因同一条**：让不掌握判据的一方去启动动作。
（项目 Rule 原话：「靠提醒才能工作的功能，该删不该补；让不掌握判据的一方启动动作，同样该删。」）

活下来的只有两个：**每轮对齐（摆事实）** + **pre-commit 门禁（不做就过不去）**。
尝试序号与实报详见 [[auto-todo-register-design]]。

### 「对齐」与「门禁」的分工（别搞混）

两者都装上了，但**职责不同，不可互相替代**：

| 对齐能做到 ✓ | 对齐不负责 ✗ |
|---|---|
| 让 LLM **每轮看见**看板现状 | 让 LLM **主动**去登记 |
| 用户一提就能**立刻接上**（不用翻文件） | 让 LLM **动手前**想起来 |
| 回答基于真实状态而非**回忆** | 替代判断 |

| 门禁能做到 ✓ | 门禁做不到 ✗ |
| 漏了也**跑不掉**（提交时必被摆出来） | 拦住「不提交就干活」的场景 |
| 不打断对话（只在 commit 时） | 判断「这算不算一个任务」（那是 LLM 的活） |

**教训**：曾因「三次没主动登记」就把 `board-align` 标成【否决】，被用户当场纠正 ——
被质疑的只是「它能不能代替 LLM 登记」，不是机制本身。
**对齐只管「看得见」，它本来就不负责「会去做」。**

### 判断该用哪一招

```
这个动作，LLM/人不做会有什么后果？
  ├─ 没后果（只是不够好）      → 别加机制。只摆事实，靠人提一句。
  └─ 有硬后果（发错版/状态失真）→ 找那个"不做就过不去"的关卡
```

**可用关卡**：`git commit`（pre-commit，今晚用了这个）/ `git push`（pre-push，跑全量测试）/
写入侧校验（如 `cmdRule` 拒超长 Rule、`markDone` 拒矛盾结语）。

## 验证

**自检判据**（写新功能前先问）—— 这是本页最该被记住的一段：
```
这个功能是在「摆事实」，还是在「替 LLM 下结论」？
  · 看板上现在有什么      → 事实 ✓
  · 我刚刚改了哪些文件    → 事实 ✓
  · → 看板无对应任务      → 结论 ✗ 越界
  · → 你忘了登记，请补记  → 劝告 ✗ 越界
```

**这个错误极易重犯**：2026-10-05 当晚，刚写下「不用技术手段」的结论，
转头就实现了三个越界功能（`wrapup --touched` 存痕迹 / `touchedFor` 读回 /
`load` 显示「→ 看板无对应任务」）。最后那句就是替 LLM 下判断，
只是把自动提醒从 hook 挪到了 load，本质没变。三处已撤回。

> ⚠ 验证这些机制时有个独立陷阱（日志报 on ≠ 真起作用；疗效不得自测），
> 已单开一页：[[mechanism-visible-vs-effective]]。

**门禁的四场景双向验证**（2026-10-05 实测通过）：

```bash
# 四场景：①改了代码没动看板→必须有提示 ②代码+todo都改→不能提示
#         ③只改文档→不能提示 ④ABS_NO_TODO=1→不能提示
sh .githooks/pre-commit | grep -c "本次提交改了代码"   # 场景①期望 1
```
