# 静默丢数据的排查顺序：先拿证据，再谈机制

## 触发场景
"写进去的东西后来不见了"、"并发下偶尔丢几条"、"任务/记录莫名少了"——
**不报错、不复现规律**的那类丢失。这类 bug 最容易查错方向，因为每一步都能编出一个
"看起来像"的因果故事。

## ❌ 反面：先猜机制（本次真实翻车记录）
一次"任务丢失"排查，连续给出三个**错误**结论：

| 结论 | 事实 |
|---|---|
| `readTodo` 有锁外读 bug | 它**根本不在**出问题的那条调用路径上 |
| 并发丢数据是锁的问题 | 锁单独压测 20 并发 **20/20 全对** |
| 看板里有脏 id 数据 | 是零宽字符被我的正则截断造成的假象 |

每次都是"读代码 → 挑一个可疑点 → 讲成结论"，而不是先把证据拿到手。
**代价：三轮方向性浪费，且把错误结论当事实交付了。**

## ✅ 正确顺序

### 1. 先确认"丢失"是真的，并拿到最小复现
不要依赖并发碰运气。**先试能否单线程串行确定性复现**：

```
abs task start T11 --note 第十一
abs task start T1  --note 第一个        ← 修复前: T11 消失, 只剩 1 条
```

**串行能复现 ⇒ 与并发无关**，立刻省掉整轮临界区排查。
反之若只在并发下丢，才去查锁。

### 2. 单独压测"被怀疑的组件"，而不是压整个链路
锁被怀疑 → 就**只压锁**（直接 import `editFile` 跑 20 并发 + 校验内容）。
整体压测发现的差异，会被链路里其它因素混淆；组件级压测能直接给该组件定罪或脱罪。

### 3. 在临界区加 trace，看写入序列（关键一步）
给"读-改-写"的临界区加临时埋点，记录每次的 **`orig` 指纹 → `write` 指纹 + 条数**：

```
SKIP  f99a367  0 -> NULL    -1     ← 探测性调用(ensureTodo)
WRITE f99a367  0 -> bd82121  1     ← 真写入
...
WRITE 50d73b1 19 -> a55bfc4 19     ← ⚠ 19 → 19, 条数没增长！
```

最后一行直接摊开真相：**这次写入读了 19 条、写了 19 条**，说明它做的是"原地改写"而非"新增"。
配合"每次 `orig` 都单调递增（0,1,2…19，无并发异常）"，可**同时排除**：
- 锁失效（序列是干净的）
- 并发覆盖（`orig` 单调）
- 读路径 bug（读到的都是最新）

**剩下唯一的可能：自己匹配到了错误的行。**于是才去看 id 匹配逻辑，一眼看到
`l.includes(id)` —— `'T11'.includes('T1') === true`。

**这一步的价值：它把"猜"变成了"排除"。**前三次是加选项，这一次是划掉选项。

## 判据（可直接套用）
1. **串行能否复现** → 决定要不要查并发
2. **组件级压测** → 给单个组件定罪/脱罪
3. **临界区 trace** → 看 `orig → write` 序列，单调性 + 条数变化直接指向根因类别
4. **证据到手前不给结论**——"像"不是判据，能排除其它可能才是
