# 概念：给共享写入路径加校验：闸门自身会引入的新失效

## 触发场景

给「所有写入都必经的那一个收口点」加格式校验 / 白名单 / 内容约束时
（如 `editFile` 的 formatGate、统一的 request 校验中间件、DB 写入前的 hook）。

三个必答问题，任一没问就会引入新失效：

## ❌ 表现

**问题 1：存量有反例吗？→ 有则整库变只读。**

校验若针对**全文**而不是**本次改动**，库里只要有一条历史脏行，升级后**所有**
写入全部失败。实测（abs v1.12.0 真机）：真库仅 1 条超长断点 + 8 条旧格式条目，
就让 `todo start` / `rule add` / `note` 全挂，只有不碰那两个文件的 `log` 能写。
用户升级后的第一件事是发现连加条规则都做不到 —— 比不加校验更糟。

**问题 2：这条违规能无损失自动修吗？→ 混为一谈必错。**

首版全拒 → 存量库锁死；第二版全放 → 闸门形同虚设。两类必须分开：

| 违规 | 判据 | 处置 |
|---|---|---|
| 空行 | 不携带信息，删了不丢东西 | **直接删**（存量自动升级）|
| 超长断点 / 旧格式条目 | 带内容，截断丢数据、改格式改语义 | **拒 + 报给人** |

**问题 3：值真传到校验点了吗？→ 声明了选项 ≠ 传下去了。**

CLI 的 `FLAG_SPEC` 是白名单，没声明的 `--flag` 被 `parseArgv` **静默丢弃**。
给 `cmdLog` 加了 kind 枚举校验，看着很稳，但 `kind` 没进 `FLAG_SPEC` →
值根本没传到函数里 → `abs log --kind note` 全写成默认 `dev`，校验零报错。

**问题 4：判据是「黑名单（什么写法非法）」还是「白名单（什么行合法）」？→ 黑名单会反复漏。**

同一个坑在 todo 闸门上复发了**三次**（2026-10-05 → 2026-10-11），每次都是**换一种写法就绕过**：

| 次数 | 当时的修法 | 下一次的绕过方式 |
|---|---|---|
| 1（10-05） | 断点 > 200 字 → 拒 | 写短一点，多写几行 |
| 2（10-05） | 断点 > 2 句 / 带列表 → 拒 | **不写成断点**，直接把总结写成裸文本行 |
| 3（10-11） | —— | 闸门只认 `- [ ]` 与 `↳ 断点:`，其余行 `continue`（**无 else 分支**）→ 裸文本行三层全部放行 |

实测第 3 次的现场：`.agents/.brain/todo.md` 的 `## Todo` 区被塞进 10 行实施报告
（「一、看图要用 preview.py…／二、…／验证方法：…」），而 `abs lint` 报 **0 problem**——
三层防线（写入闸门 / 形状闸门 / lint）没有一层看它，因为**每层都只检查自己认识的那几种形态**。

根因不在「判据不够严」，而在**判据的极性**：

- 黑名单（列出非法写法）→ 要穷举未来的写法，永远漏；每修一次只是把当前的写法堵上。
- 白名单（列出合法写法）→ 没列进来的都非法，换写法自动落回拦截。

这里的合法集很小且很稳定（任务行 / 断点行 / 空行 / 标题），所以白名单是正确形状：

```js
// src/todo/common.js — 合法行白名单，闸门与 lint 共用同一份判据
export function isAllowedTodoLine(l) {
  const t = l.trim();
  if (!t) return true;                       // 空行
  if (/^#{1,3}\s/.test(t)) return true;      // 标题
  if (isTaskLine(l)) return true;            // 任务行
  if (isChildLine(l)) return true;           // ↳ 断点
  return false;                              // 其余一律非法
}
```

两个配套约束：

1. **按区判，不按全文判**：只对 `## Todo` 区生效。Done/Archived 区有日期分组
   （`### 2026-10-11`）与归档链接（`- log-日期 完成任务 N 条` 这种带方括号的链接行），
   按 Todo 区白名单判会误报一片。
2. **闸门与 lint 必须同源**（同一函数，不是两份一样的代码）：闸门拦新写入，
   lint 抓老存量。两份实现必然漂移，那就又回到「改一份不算改」。

### 为什么第三次才发现「判据极性」是根因

前两次的记录都写着「补充判据 X」，读起来像是进展；但**每次补的都是一个更细的黑名单条目**。
判断信号：如果同一个地方**第二次**加校验，就该停下来问「我在补黑名单还是改白名单」，
而不是接着补第三条更细的规则。**「同一个坑第二次出现」本身就是判据选错极性的证据。**

## 🛠 解法

1. **区分存量与新增**：写入前就有的违规 → 放行（交给 lint/体检报出）；本次写入
   引入的 → 拒绝。用**内容签名**比对（去空白 + 截断），不用行号 ——
   插入一行会让后面所有行号位移。
2. **逐条判「能否无损失重建」**：能修的直接修（存量自动升级），不能修的才拒。
3. **选项改三处 + 断言值生效**：声明（FLAG_SPEC）、传参（调用点）、校验（函数）；
   测试要断言**值真的落盘**，不是「没报错就算过」。
4. **闸门先归一、再校验**（顺序不能反）：旧标记/旧格式要在校验**之前**归一，
   否则存量老文件全被当成「非法新格式」卡死（首版反了 → 7 个测试红）。

## 验证

- 真库副本上跑四类写入（todo/rule/note/log）：**全部成功**（存量不锁死）
- 同一副本上制造新违规（超长断点、非法标签）：**仍被拒**（闸门没失效）
- `abs lint` 仍报出存量问题条数不变（存量没被静默放过）
- 旧格式自动升级：造四区制老文件 + 写新任务 → 归一为两区制，内容零丢失
