# 过滤要看所有出口：入口排了，出口不排就绕过去

检索里「排掉某一类页」不是一个判断，是**一对**判断。种子入口排了，扩散出口不排，那类页会顺着邻居链接爬回来。

## 触发场景

- 检索里加了一条排除规则（流水页、被推翻的页、未填的页）
- 当时验证「搜这个词不再出现它了」，看着是好的
- 但那些页与正常页之间有双链

## ❌ 表现（实测两次，同一处）

`src/brain/db.js` 里检索分两步：`search()` 拿种子 → `illuminate()` 从种子扩散。

**第一次（2026-11-02）**：`search` 排除了 `superseded`，出口没排。

> 实测旧结论页自己不出现在种子里，却被邻居扩散点亮（亮度 0.24 带 ↝）。

**第二次（2026-11-05）**：`search` 排除了 `unfilled`（空骨架会话页），出口又没排。

```
知识页 real 链到一张空骨架 sk1
查「缓存穿透」→
  ████████████ 1.00 L4 spread/concepts/real
  ███ 0.24 L5 spread/sessions/session-2026-11-05-saaaa0001 ↝   ← 又漏出来了
```

**为什么低亮度仍然有害**：带 `↝` 标记的结果看起来像「相关内容」，实际是空骨架。
一个明确被排除的东西以低亮度出现在结果里，比完全不出现更误导。

## 🛠 做法

同一份排除条件，**两处查询都要写**：

```js
// 入口：拿种子
WHERE fts MATCH ? AND n.is_ledger = 0 AND n.unfilled = 0 AND n.status != 'superseded'

// 出口：扩散时取页面
SELECT ... FROM nodes WHERE id = ? AND is_ledger = 0
  AND status != 'superseded' AND unfilled = 0
```

**判据：加任何一条「这类页不该出现」的规则时，先 grep 所有会产出页面的查询。**
`grep -n "FROM nodes WHERE id" src/brain/db.js` —— 出口通常长得和入口很不一样（一个走 FTS，一个走 id 主键），所以漏掉很难被发现。

## 更一般的形状

这是「过滤器只装了一条管」的通病，本仓已有多例：

| 位置 | 入口/一侧 | 另一侧 |
|---|---|---|
| 检索排除 | `search` 的 FTS 查询 | `illuminate` 的 id 查询 |
| 格式闸门 | 写入校验 | 读取时的迁移 |
| 部署 | 自己写的注册文件 | 外部 store 里被读走的那份 |

共同点：**两个地方都在做同一件判断，但代码形状不同，所以不会有人想着一起改。**

## 验证

```bash
node --test test/brain-graph.test.js   # 两条：种子排除 + 扩散排除
```

实测（2026-11-05）：造一张链到空骨架的知识页，修复前空骨架以 `↝ 0.24` 出现在结果，
修复后不再出现；知识页本身仍是 1.00 居首。
