# 概念：工具的「空结果」不等于「没有输出」

## 触发场景
用一个**会筛选/摘要/分页**的工具看数据，而它返回了空（或某一段是空的）：
搜索工具、带 query 的批量执行工具、日志聚合器、`grep` 类过滤器。
正要把这个"空"当成一个事实来推断时 —— **先停一下**。

一句话判据：**我看到的"空"，是"源头没有"，还是"中间那层把它滤掉了"？**

## ❌ 表现
**把"没匹配"读成"不存在"，然后带着这个错误结论继续往下走。**

2026-10-06 本仓实测（`ctx_batch_execute`）：
该工具返回的 section 是**按 query 匹配出来的片段**，未命中的段**显示为空**。
于是出现：

```
query: ["测试怎么跑", "文件结构", ...]
→ 全部返回 "No matching sections found"
```

而此时 `git status` / `git log` **明明有内容**。当时的读法是
"空 → 命令没输出 → 工作区干净"，**差点带着错误结论走**。

> 危险点：它不像报错那样挡你，而是给你一个**看起来像事实的空值**。
> 而"仓库干净"这种结论一旦被接受，后面所有推理都建立在它上面。

## 🛠 解法
**核实空值的来源，而不是相信它。**

1. **判据**：工具的空段 ≠ 空输出。区分两者只能**直接跑原始命令看 stdout**：
   ```bash
   git status --short        # 直接看，不经筛选层
   ```
2. **优先用"不能为空"的工具看事实**：`cat` / `git status` 这类原样输出的命令，
   在批量工具不适合当证据源时直接用。
3. **给批量工具加一条"总览类"查询**（如 `file-tree`、`layout`），它的段通常不为空 ——
   **如果连它都空，那才是真的没输出**。用这个作对照信号。

### 通用形态（比这个具体工具更值钱）
任何**"输入 → 筛选/摘要 → 呈现"**的中间层都有这个问题：

| 层 | 空值的两种含义 |
|---|---|
| 搜索工具 | 没匹配？还是源头没有？ |
| 日志聚合 | 没匹配关键词？还是没日志？ |
| 摘要/截断 | 真没有？还是被截掉了？（见 [[summary-truncation-hidden-cause]]） |
| `grep` 无输出 | 真没有？还是路径错了 / 权限不够被吞了？ |

**判据：把这一层的输出当"证据"之前，先确认这一层有没有过滤能力。**

## 验证
看一个**已知非空**的源，能否在工具里表现为空：

```bash
# 已知有内容
git log --oneline -3              # 有输出

# 再经筛选层看它 —— 若为空，就是"被滤掉"而非"没有"
# （用不匹配的 query 跑批量工具即可复现）
```

复现即证明：空值来自筛选层，不是源头。
本仓实测：同一批命令，`git status` / `git log` 有内容，而批量工具对应段为空。
