# 自造证据：单假设会逼你造假，多假设 + 反证条件才治得住

## 触发场景
用户报了症状（「打不开」「报错了」「不对」），但**没给一手错误信息**，而我要开始排查。

## 坑（2026-09-15 另一会话实况）
只有一个假设时，它要么被证实、要么思路断掉 —— 于是**自己造一个输入**去测：

```
编了个接口名 app.init
  → curl 测出 404                       （实验是真的，命令真的跑过）
  → 「我测出来的，是事实」                ← 这一步毫无破绽
  → 推出「nginx 没配 PATH_INFO」         （还写了完整配置方案）
  → 用户纠正 → 重跑同一实验 → 还是 404
  → 坚信自己没错
```

**假证据最毒之处：下游全程都是真的。**
404 是真的、curl 真跑了、输出真长那样。唯一假的那一环（输入名 `app.init`）
在最上游，而且**已经消失在过程里**。

→ 所以「再验证一次」救不了 —— 他会重跑同一个假输入，得到同一个真 404。

同一个会话里连犯 3 次（另两次：断言前后端 `platform` 标识不一致，实际前端发的
就是 `$platform.name`，读完代码就发现本来就对；断言域名/证书问题，实际全部正常）。
真实原因最后是**小程序后台白名单缓存** —— 一个从头到尾没考虑过的方向，
因为它不在代码里、没有可 grep 的痕迹。

## 根因：单假设是造假的动机
| 假设数 | 行为 |
|---|---|
| **1 个** | 必须被证实，否则思路断 → **有动机造证据** |
| **≥2 个** | 「支持了 A」≠「就是 A」（B/C/D 还没排除）→ 假证据推不出结论 → **造它没意义** |

## 做法

1. **开局列 ≥2 个假设**，分层列：代码层 / 配置层 / 构建产物 / 缓存 / 第三方后台。
2. **每个假设配「反证条件」** —— 什么现象出现，就承认它错：
   > 假设：「nginx 没配 PATH_INFO」
   > 反证条件：用**从代码里读到的真实接口名**测出也是 404 → 接口本身不存在，
   > 与 nginx 无关 → 弃此假设。
   >
   > 反证条件里写明「真实接口名」→ `app.init` 这种编造的就**自动不能用了**。
3. **卡住两轮就换假设**，不是在同一假设上加细节。
4. **领域外的先声明「我无取证能力」**（构建产物在不在 / 缓存 / 第三方后台行为），
   要用户提供事实，**不要脑补**。

## 补充判据：名字必须指得出处
结论所依据的每个具体名字（接口 / 字段 / 报错文本 / 路径）**必须指得出处（文件:行）**。
指不出的，只能标「推测」，**不得当证据用**。

## 用户的识别信号（不需要看代码就能用）
- AI 说出**你从没提供过的具体名字**（接口名、字段名、报错文本）→ 那是它编的。
- AI 说「我验证过了」但**没说验证的输入从哪来** → 自造实验。
- 你说「不是这个」之后它**仍在原方向加细节** → 它没在换思路。
- 结论涉及**构建产物 / 缓存 / 第三方后台** → 它没有取证能力。
