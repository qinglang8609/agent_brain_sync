# 状态不完整时不替用户决定

当操作遇到「前置条件没满足」时（如子任务未勾完就要 done），正确处理只有一种：**明确拒绝，把选择权交回**。任何自动兜底都是替用户做决定。

## 触发场景

给「完成」「归档」「删除」这类**终态操作**加处理逻辑，而对象可能处于不完整状态时。

## ❌ 表现

2026-10-18 实测，四种自作聪明的处理各错一次：

| 兜底方式 | 为什么错 |
|---|---|
| 随父任务一起进 Done | 未完成的子项被折叠计数吞掉，永远看不见 |
| 升格为独立任务留着 | 用户看到的是「我没勾的东西冒出来了」，状态被篡改 |
| 造个占位任务 | 无中生有，看板出现用户从没写过的东西 |
| 原地留着不动 | 成孤儿，后续归档清理时静默消失 |

四种的共同点：**都替用户做了「这个子任务该怎么办」的决定**，而程序不掌握这个判据。

## 🛠 解法

拒绝，并给出用户可执行的下一步：

```js
if (hasUncheckedChildren(task)) {
  return `✗ ${task.id} 还有 ${n} 个未勾子项 —— 先勾完，或显式说明要一起完成`;
}
```

判据：**程序能做的是「报告状态」，不是「决定状态的归属」。**

## 验证

跑对应测试确认：带未勾子项的 done 被拒绝且看板无变化。
破坏验证：把拒绝改成任一兜底，应当有测试变红——若不红说明缺覆盖。

反向的边界（已知且已验）：带未勾子项的 `done` 在**升格**场景下是允许的，
但那要用户显式要求，不是程序自动判断。
