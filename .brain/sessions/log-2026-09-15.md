# 会话 2026-09-15 — fnos 半升级定位 → 进化评估 → abs concept → 发布 1.8.4~1.8.6

## 一、起因：fnos 上 `abs install` 四宿主全失败

用户贴出报错，四宿主（claude-code / codex / opencode / pi）齐刷刷：

```
ENOENT: no such file or directory, open
  '/root/.nvm/.../node_modules/@fanchao8609/agent_brain_sync/skill/SKILL.md'
```

## 二、定位（证据链，非猜测）

先怀疑自己刚发布的包，于是**把发布产物拉下来实测**，而不是读源码推断：

| 检查 | 结果 |
|---|---|
| 本仓 `src/install.js` | 动态遍历子目录（`ALL_SKILLS`）→ 正确 |
| 本仓 `skill/` | `abs-agent-brain-sync/` + `abs-bug-hunter/` 子目录布局 |
| npm 上 1.8.3 tarball | 子目录布局 + 遍历代码 → **包是好的** |
| **1.8.2 的 `install.js`** | `readdirSync` 出现 **0 次**，只认写死的扁平 `skill/SKILL.md` |
| 报错里的路径 | 正是 1.8.2 那个扁平字符串 |

**结论**：fnos 跑的是 **1.8.2 的代码 + 1.8.3 的 `skill/` 布局** = 半升级。
补充证据：改目录布局（`26f7601`）与改读取代码是**同一个 commit** → 任何已发布版本内部都自洽，
不存在"包里漏改"，所以这是**陈旧安装**，不是打包 bug。

## 三、关键发现：守卫治不了报错的那个形态，但治得了反向

我第一轮说"加个守卫就能避免这次绕圈"——**不准确**，当场纠正：

| 形态 | 谁的问题 | 守卫管不管 |
|---|---|---|
| 旧代码 + 新布局（**fnos 这次的形态**） | 1.8.2 的代码 | ❌ 管不了 —— 旧代码改不动 |
| 新代码 + 扁平旧布局 | 当前代码 | ✅ 管住了 —— 原本**静默装 0 个** |

**第 2 类更毒**：`readdirSync` 只看 `isDirectory`，扁平的 `SKILL.md` 是**文件**被跳过
→ `ALL_SKILLS = []` → **静默装 0 个 skill、一句不说**。

### 6.2 「lint 强制尾巴能解决文档没收尾吗」→ 不能，位置错了
lint 是**事后检查**。反证：09-12 那 3 条占位链 lint 报了 2 天仍未处理。
**根因**：`concepts/` 页没有任何代码写入路径 —— 骨架只写在 skill 文字里，无执行点。
对照 `sources/` 页结构整齐（模板在代码里）。→ 见 [[learning-loop-collect-distill-deliver]] 第 4 节。

### 6.3 解法：`abs concept`（写入侧定结构）+ NO-TAIL 判据

- 判据两处修正：**放宽**（认 11 个动作词，因实测 `## ✅ 处置` 出现 17 次 > `## 🛠 解法`，
  只认「验证」误报 7/11=64%）+ **收紧**（要求段内有真内容，否则未填骨架自动合格）
- 本仓 26 页 NO-TAIL 归零（补了 2 页真缺尾）
