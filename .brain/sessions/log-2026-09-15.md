# 会话 2026-09-15 — fnos 半升级定位 → 进化评估 → abs concept → 发布 1.8.4~1.8.6

## 一、起因：fnos 上 `abs install` 四宿主全失败

用户贴出报错，四宿主（claude-code / codex / opencode / pi）齐刷刷：

```
ENOENT: no such file or directory, open
  '/root/.nvm/.../node_modules/@fanchao8609/agent_brain_sync/skill/SKILL.md'
```

## 二、定位（证据链，非猜测）

先怀疑自己刚发布的包，于是**把发布产物拉下来实测**，而不是读源码推断：

| 检查 | 结果 |
|---|---|
| 本仓 `src/install.js` | 动态遍历子目录（`ALL_SKILLS`）→ 正确 |
| 本仓 `skill/` | `abs-agent-brain-sync/` + `abs-bug-hunter/` 子目录布局 |
| npm 上 1.8.3 tarball | 子目录布局 + 遍历代码 → **包是好的** |
| **1.8.2 的 `install.js`** | `readdirSync` 出现 **0 次**，只认写死的扁平 `skill/SKILL.md` |
| 报错里的路径 | 正是 1.8.2 那个扁平字符串 |

**结论**：fnos 跑的是 **1.8.2 的代码 + 1.8.3 的 `skill/` 布局** = 半升级。
补充证据：改目录布局（`26f7601`）与改读取代码是**同一个 commit** → 任何已发布版本内部都自洽，
不存在"包里漏改"，所以这是**陈旧安装**，不是打包 bug。

## 三、关键发现：守卫治不了报错的那个形态，但治得了反向

我第一轮说"加个守卫就能避免这次绕圈"——**不准确**，当场纠正：

| 形态 | 谁的问题 | 守卫管不管 |
|---|---|---|
| 旧代码 + 新布局（**fnos 这次的形态**） | 1.8.2 的代码 | ❌ 管不了 —— 旧代码改不动 |
| 新代码 + 扁平旧布局 | 当前代码 | ✅ 管住了 —— 原本**静默装 0 个** |

**第 2 类更毒**：`readdirSync` 只看 `isDirectory`，扁平的 `SKILL.md` 是**文件**被跳过
→ `ALL_SKILLS = []` → **静默装 0 个 skill、一句不说**。

## 六、下午续：把「进化」这个话题聊到底（本会话真正的主题）

上午修完 fnos 后，用户连续追问三件事，脉络是从「能不能进化」收敛到「怎么送达」。

### 6.1 「图谱能积累经验实现进化吗」→ 实证：不能
用 git 查 Rules 的真实积累路径（见 [[learning-loop-collect-distill-deliver]]）：
14 条里 **13 条来自两次人工注入**，09-13 之前根本没有 Rules 区。
三环节里只有「采集」（hook 写日志）是机械可靠的。
**结论：系统有记忆，没有「改变自己的机制」，只有「被你改变的通道」。**

### 6.2 「lint 强制尾巴能解决文档没收尾吗」→ 不能，位置错了
lint 是**事后检查**。反证：09-12 那 3 条占位链 lint 报了 2 天仍未处理。
**根因**：`concepts/` 页没有任何代码写入路径 —— 骨架只写在 skill 文字里，无执行点。
对照 `sources/` 页结构整齐（模板在代码里）。→ 见 [[learning-loop-collect-distill-deliver]] 第 4 节。

### 6.3 解法：`abs concept`（写入侧定结构）+ NO-TAIL 判据
- 新命令生成四段骨架（头/中/尾），**只给结构不给内容** —— 判断仍归人
- 判据两处修正：**放宽**（认 11 个动作词，因实测 `## ✅ 处置` 出现 17 次 > `## 🛠 解法`，
  只认「验证」误报 7/11=64%）+ **收紧**（要求段内有真内容，否则未填骨架自动合格）
- 本仓 26 页 NO-TAIL 归零（补了 2 页真缺尾）

### 6.4 发布 1.8.5 → 1.8.6（含一次顺序错误）
`npm publish` 1.8.5 成功，**但我先发版再改 skill** → 产物 skill 不含 `abs concept` 文档
（命令存在但没人知道；且用户 `npm i -g` 会被旧 skill 覆盖宿主副本）。
只能补发 **1.8.6**（纯文档）。判据已记进 [[npm-publish-flow]]：**文档和代码在同一个
tarball 里，必须同批改完再发。**

另：本机网络一度全断（DNS 被 fake-ip 代理劫持到 `198.18.x.x` 但代理进程没跑），
由用户重启代理后恢复 —— 不是 npm 配置问题。

## 七、晚间：sessions/ 命名契约 + 跨 6 项目治理

### 7.1 起因：codebuddy 的 sessions/ 乱成一团
同一天 5 个文件 5 种 tags；4 个 `tags: [source]` 页错位；09-14 同天两份快照。

### 7.2 定契约（skill）+ 加检查（lint）
`log-<日期>.md` 一天一文件；归档并入其 `## 📦 任务归档` 段（`abs todo archive` 自动）。
新增 `SESSIONS-SPLIT` / `SESSIONS-MISPLACED` / `SESSIONS-NAMING` 三条检查。

### 7.3 归档行为变更（用户定为标准）
`slugFor` 从 `<日期>-todo归档` 改为 `log-<日期>`；`renderArchivePage` → `upsertArchiveSection`
（段级 upsert：段外手写内容逐字保留；无快照则建只有归档段的页）。

### 7.4 治理 6 个项目（全部 SESSIONS 归零）
```
agent_brain_sync  4 归档→并入 log；lint 3→0（首次归零）
codebuddy         4 归档 + 4 错位页 + 09-14 双快照 + 33KB 归档拆 3 页
zj_shop           3 归档 + 09-09 双快照

~/.brain          2 份外部会话历史归档 → 打 archive 标签

```
**每处迁移都做了**：先备份 → 逐行核对计数无损 → 发现真丢失就补
（codebuddy 的 `ui-fixes` 有 2 项 log 里没有，补了）。

### 7.5 顺手抓到 3 个工具缺陷（都有测试钉住）
1. 日期正则 `^\d{4}-` 匹配不上规范名 `log-…` → 「一个 log- + 一个杂文件」数成 1 个（漏报）
2. `SESSIONS-NAMING` 缺失：旧命名**单独存在**时不报（~/Docker 四天全漏）
3. 豁免 `\barchive\b` 误匹配 `todo-archive` → 老式归档页全被豁免
4. `UNRESOLVED-CONFLICT` 用裸子串 → 任务描述提到"知识冲突"即误报

**通则已沉淀**：[[naming-contract-and-judge-precision]] —— 判据看结构不看关键词。
